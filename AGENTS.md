# AGENTS.md

## Communication and ownership

- Communicate with the repository owner in Ukrainian unless the owner requests another language.
- Execute clear implementation requests directly; ask only when an irreversible external action or an ambiguous product decision requires it.
- Do not edit this file without explicit owner approval. Keep repository-specific rules here.
- Leave no traces of AI authorship or AI tooling in committed code, configuration or comments: remove AI attribution, generated-by markers, assistant/model/tool names that identify authorship, prompt/chat residue, watermarks and AI commit trailers. Keep only AI/service references required for actual product behavior, security or legally required third-party notices; never remove or conceal those.

## Project boundaries

- Work on this repository only in its GitHub repository: branches, pull requests and `main`. Do not create, link or use a Lovable project for its code, firmware, card or documentation.
- `esphome/grid-monitor.yaml` is the source of truth for firmware behavior and entity names.
- The ESPHome device is the backend. The Home Assistant frontend must not duplicate measurement, outage, tariff or counter logic.
- Preserve the distinction between unavailable ESP/PZEM states and a confirmed inverter state.
- Keep secrets in `esphome/secrets.yaml` only; never commit credentials, tokens or real local network values.

## HACS card architecture

- The installable frontend artifact is the root-level `grid-monitor-card.js`, registered as `grid-monitor-card`.
- Keep the card dependency-free: vanilla JavaScript, Web Components and Home Assistant's existing `hass` object only.
- Keep `hacs.json` accurate: `filename` must point to the root card and `content_in_root` must remain `true`.
- Do not add a custom integration merely to make HACS recognize the repository; ESPHome already provides the device integration.
- The native YAML dashboard remains a supported fallback and must not be removed when the card changes.

## UX invariants

- Preserve the dark navy/neon visual language: cyan-blue live data, green healthy state, amber inverter state and red quality alarms.
- The card must be responsive in narrow Android Home Assistant layouts as well as desktop masonry layouts.
- User-facing labels and statuses require a localization dictionary. Support Ukrainian and English; allow an explicit `language` override and otherwise follow the Home Assistant locale when available.
- Missing, `unknown` and `unavailable` entities must render a clear placeholder and must never throw or break the entire card.
- Destructive or state-changing buttons must call only the configured Home Assistant entity service and require confirmation where appropriate.

## Entity conventions

- Default entity IDs use the ESPHome slug `grid_monitor` and follow Home Assistant's lower-case entity IDs.
- Allow per-entity overrides in card configuration so devices with a different ESPHome name remain usable.
- New firmware entities must be reflected in the card, native dashboard coverage check and documentation.

```bash
print('hacs.json: OK')
PY

```

Also run the ESPHome-secret-aware YAML parser and dashboard/entity coverage check when firmware or dashboard mappings change. Do not claim live Home Assistant validation unless it was actually performed.
- Keep routine pull-request validation lightweight: run syntax, unit/contract, JSON and YAML checks; do not install or compile the full ESPHome toolchain for every change. Reserve firmware compilation for firmware-specific/manual or scheduled validation.
- Before waiting on GitHub checks, inspect branch protection and actual check-runs. Do not block on an advisory app suite that is not required and has zero check-runs; required checks and concrete review findings still gate merging.

## Release versioning

- Use the release format `YYYY.MM.N`, for example `2026.11.1`: `YYYY` is the four-digit calendar year, `MM` is the two-digit calendar month, and `N` is the release sequence number within that month, starting at `1`.
- Do not create, tag, publish, or increment a release version unless the repository owner explicitly requests it.
- When the owner requests a release, use the version they specify. If they ask to update or re-create an existing version, replace the existing release/tag for that version instead of minting a new version, unless they explicitly request a different version.
- Publish a release only after the approved changes are on `main` and the applicable validation checks have passed.

## HACS update delivery

- A merge to `main` alone does not update an existing HACS installation. Because this repository publishes releases, HACS takes the plugin files and remote version from the latest full GitHub Release and its tag; changes only on the branch are not enough.
- **Mandatory tag/release sync on every card update:** Whenever `grid-monitor-card.js` or HACS-related configuration is modified and merged into `main`, the agent MUST immediately make the merged files available through the HACS release source. A merge to `main` alone is never delivery.
- **When the owner does not request a new release:** Do NOT create a GitHub Release, increment the version, or leave the existing release tag on an old commit. Keep the existing latest Release entry and version, then move its existing tag to the new merge commit on `main`, exactly as follows (replace placeholders with the actual tag and full commit SHA):
  ```bash
  git tag -f <existing-version> <main-merge-commit>
  git push origin refs/tags/<existing-version> --force
  ```
  This intentionally re-targets the existing release tag; it is not a new Release or version. HACS downloads the source at that tag, so a reinstall/redownload from the existing HACS repository then includes the merged changes. Do not substitute a `main`-branch install or ask the owner to perform the retagging when this workflow is requested.
- If the owner explicitly requests a new release/version, publish that requested version instead. Otherwise reuse and retag the latest existing release/tag as above. After either path, verify that the release tag resolves to the intended merge commit and that it contains the updated root `grid-monitor-card.js`.
- Do not report HACS delivery complete after merging or refreshing repository metadata alone. Tell the owner to use HACS → repository menu → **Update information**, then **Redownload** (or **Update**) the Dashboard repository; metadata refresh does not download the JavaScript. Also remind the owner to hard-refresh the browser or reload Home Assistant resources (`Ctrl+F5` / `Cmd+Shift+R`) to bust the Lovelace cache.
- For manual/private testing, add the GitHub repository in HACS as a custom repository of type **Dashboard**. Do not claim that this makes the repository searchable in the default HACS catalog; default-catalog inclusion requires a separate submission and acceptance by `hacs/default`.

## GitHub workflow

- Inspect `origin/main` and open PRs before changes.
- Use a focused feature branch and conventional commits.
- Keep firmware, frontend, documentation and tests understandable in the same change when they form one installable feature.
- Open a PR with a concise summary and validation evidence. Merge only after checks pass, then verify the merge commit and final files on `main`.
- For implementation work the owner requested, merge the PR into `main` without asking for separate merge approval once it is mergeable, every required check passes with no errors, all required reviews are complete, and no unresolved blocking findings remain. Do not leave a clean PR open after the requested work is complete. If a check, review, or finding is not clean, fix it and re-check before merging.
- Do not force-push or rewrite shared history. Delete merged feature branches when appropriate.
